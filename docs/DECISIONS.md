# DECISIONS — บันทึกการตัดสินใจของโปรเจกต์ (ADR)

> **ADR = Architecture Decision Record** — บันทึกว่า "ตัดสินใจอะไร ตอนไหน เพราะอะไร"
> schema กับ SQL บอกได้แค่ว่า *ทำอะไร* แต่บอกไม่ได้ว่า *ทำไมไม่ทำอีกแบบ*

## ADR-001 — ทำอาหารแล้วระบบหักวัตถุดิบตามสูตร

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ร่างแรกของ proposal ให้สมาชิกบันทึกได้ว่าทำเมนูอะไร แต่จำนวนของในตู้ไม่ลดลง ทางแก้มีสองทาง คือให้ระบบหักตามสูตรเอง หรือให้สมาชิกไปแก้จำนวนเอง

### ปัญหาที่เกิดถ้าไม่หัก

จำนวนในตู้จะไม่ลดลงเลย บ้านที่ทำไข่เจียวไปหลายครั้งจนไข่หมด ระบบก็ยังเห็นไข่เท่าเดิม และยังแนะนำไข่เจียวต่อ ส่วนทางที่ให้สมาชิกแก้เอง ตัวเลขจะถูกก็ต่อเมื่อทุกคนจำได้ทุกครั้ง

### การตัดสินใจ

สมาชิกบันทึกแค่ว่าทำเมนูไหน แล้วระบบหักวัตถุดิบตามปริมาณในสูตรเอง

- หักเฉพาะล็อตในตู้บ้านตัวเองที่ยังไม่หมดอายุ โดยหักจากล็อตที่หมดอายุเร็วที่สุดก่อน
- เช็คก่อนว่าวัตถุดิบทุกอย่างในสูตรพอ (นับเฉพาะล็อตแบบข้อบน) ถ้าอย่างใดอย่างหนึ่งไม่พอ ไม่บันทึกอะไรเลยทั้งรายการ
- การบันทึกประวัติการทำอาหารกับการหักของ อยู่ในธุรกรรม (transaction) เดียวกัน

### ผลที่ตามมา

- ✅ จำนวนในตู้ตรงกับของจริงโดยไม่ต้องมีใครจำ
- ⚠️ SQL ในขั้น 3 ซับซ้อนขึ้น เพราะต้องหักหลายแถวในคราวเดียว
- ⚠️ คำสั่งที่หักไล่ทีละล็อต ถ้าของไม่พอจะหักเท่าที่มีโดยไม่แจ้ง error ขั้นเช็คก่อนหักจึงตัดทิ้งไม่ได้

## ADR-002 — รายการซื้อของกับราคาไม่อยู่ในขอบเขต

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ระหว่างร่าง proposal เคยมีฉบับที่ส่งของขาดเข้ารายการซื้อของ และเก็บราคาไว้คิดค่าใช้จ่าย

### การตัดสินใจ

ตัดรายการซื้อของกับราคาออกจากขอบเขต

### ผลที่ตามมา

- ✅ ข้อมูลหลักเหลือ 8 อย่าง ขอบเขตพอดีกับโครงงานกลุ่ม
- ⚠️ เอกสารและการนำเสนอห้ามอ้างว่าระบบช่วย "ลดค่าใช้จ่าย" เพราะไม่มีข้อมูลราคาให้พิสูจน์

## ADR-003 — ต้องมีการบันทึกการทิ้งของ

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ของในตู้ออกได้สองทาง คือใช้ทำอาหาร กับทิ้งเพราะหมดอายุหรือเสีย ถ้าบันทึกได้แต่ทางแรก ของที่ทิ้งไปแล้วจะยังค้างอยู่ในตัวเลข

### การตัดสินใจ

สมาชิกบันทึกว่าทิ้งของจากล็อตไหน จำนวนเท่าไร แล้วระบบหักออกจากล็อตนั้น และเก็บเป็นประวัติการทิ้ง (ล็อต / จำนวน / วันที่ทิ้ง)

- ทิ้งเกินกว่าที่ล็อตเหลืออยู่ไม่ได้
- ทิ้งได้เฉพาะของในตู้บ้านตัวเอง
- ล็อตที่ทิ้งหมดแล้วไม่ลบออก ประวัติการทิ้งจะได้ยังอ้างถึงได้
- การบันทึกประวัติการทิ้งกับการหักจากล็อต อยู่ในธุรกรรม (transaction) เดียวกัน

### ผลที่ตามมา

- ✅ จำนวนในตู้ = ของที่ซื้อ − ของที่ใช้ทำอาหาร − ของที่ทิ้ง
- ✅ ดูย้อนหลังได้ว่าบ้านไหนทิ้งอะไรไปเท่าไร
- ⚠️ ข้อมูลหลักเพิ่มเป็น 8 อย่าง

## ADR-004 — วัตถุดิบหนึ่งอย่างใช้หน่วยมาตรฐานเดียว

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ระบบต้องเทียบปริมาณในสูตรกับจำนวนในตู้ ถ้าบ้านหนึ่งบันทึกไข่เป็น "1 แผง" แต่สูตรใช้ "2 ฟอง" ระบบจะเทียบ 1 กับ 2 แล้วสรุปว่าไข่ไม่พอ ทั้งที่จริงมี 30 ฟอง

### การตัดสินใจ

วัตถุดิบแต่ละอย่างมีหน่วยมาตรฐานเดียว เก็บไว้ที่ข้อมูลวัตถุดิบ ทั้งล็อตในตู้และปริมาณในสูตรใช้หน่วยนี้ ระบบจึงไม่ต้องแปลงหน่วย

### ผลที่ตามมา

- ✅ query เทียบปริมาณได้ตรงๆ
- ⚠️ ตอนบันทึกของเข้าตู้ต้องกรอกเป็นหน่วยมาตรฐาน เช่น ไข่ 1 แผงต้องกรอกเป็น 30 ฟอง

## ADR-005 — เลือก DBMS

**วันที่**: 11 พ.ย. 2026 · ตัดสิน 13 พ.ย. 2026 (ประชุมครั้งที่ 1) · **สถานะ**: ✅

### บริบท

ขั้น 3 ต้องเขียน SQL จริง ไวยากรณ์บางส่วนต่างกันในแต่ละ DBMS เช่น ฟังก์ชันวันที่ จึงต้องเลือกก่อนเขียนไฟล์ SQL

### ที่รู้ตอนเลือก

- สไลด์หน้า 9 ยกตัวอย่าง DBMS 4 ตัว คือ MySQL, PostgreSQL, Oracle, SQL Server
- สไลด์ไม่ได้บอกว่าโครงงานต้องใช้ตัวไหน กลุ่มเลือกเองได้

### การตัดสินใจ

ใช้ **PostgreSQL** ไฟล์ SQL ทุกไฟล์ใน [`../database/`](../database/) เขียนตามไวยากรณ์ของ PostgreSQL

### ผลที่ตามมา

- ✅ เริ่มเขียนไฟล์ SQL ได้ ไม่ต้องรอเลือกแล้ว
- ⚠️ ทุกคนต้องติดตั้ง PostgreSQL หรือต่อเครื่อง database เดียวกันได้ วิธีรันอยู่ใน [ADR-009](#adr-009--เลือกภาษาและวิธีรันเว็บแอป)

## ADR-006 — รายชื่อสมาชิกไม่ขึ้น repo สาธารณะ

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: 🔁 ถูกแทนที่ด้วย [ADR-007](#adr-007--รายชื่อสมาชิกและรหัสนักศึกษาขึ้น-readme)

### บริบท

repo นี้เป็นสาธารณะ ใครก็เปิดดูได้ ส่วนแบบฟอร์มของอาจารย์ต้องใส่ชื่อ นามสกุล รหัสนักศึกษา และอีเมลของสมาชิก

### การตัดสินใจ

ชื่อ นามสกุล รหัสนักศึกษา และอีเมลของสมาชิก ใส่เฉพาะในแบบฟอร์มที่ส่งอาจารย์ ไม่ใส่ในไฟล์ใดของ repo เอกสารใน repo เรียกสมาชิกว่า "คนที่ 1–6"

### บังคับใช้อย่างไร

[แม่แบบ PR](../.github/pull_request_template.md) มีข้อนี้ใน checklist คนรีวิวต้องตรวจก่อน approve

## ADR-007 — รายชื่อสมาชิกและรหัสนักศึกษาขึ้น README

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅ · แทนที่ [ADR-006](#adr-006--รายชื่อสมาชิกไม่ขึ้น-repo-สาธารณะ)

### บริบท

ADR-006 ไม่ใส่รายชื่อสมาชิกใน repo เพราะ repo เป็นสาธารณะ ต่อมาเปลี่ยนให้หัวข้อทีมใน README บอกได้ว่าใครอยู่ในทีม

### การตัดสินใจ

หัวข้อทีมใน [README](../README.md#-ทีม-7-คน) ใส่ชื่อ นามสกุล และรหัสนักศึกษาของสมาชิกทั้ง 7 คน ส่วนอีเมลของสมาชิกใส่เฉพาะในแบบฟอร์มที่ส่งอาจารย์ ไม่ใส่ใน repo

### ผลที่ตามมา

- ✅ คนที่เปิด repo รู้ว่าใครอยู่ในทีม
- ⚠️ repo เป็นสาธารณะ ใครเปิดก็เห็นชื่อกับรหัสนักศึกษา และถึงจะลบออกทีหลัง ประวัติ commit ก็ยังเก็บไว้

## ADR-008 — ทำเป็นเว็บแอปที่ใช้งานได้จริง

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

งานส่ง 4 ชิ้นของอาจารย์ (Lecture 1 หน้า 11) เป็นงานออกแบบและสร้างฐานข้อมูล ไม่มีหน้าเว็บหรือ API

### การตัดสินใจ

ระบบมี 4 ส่วนตามผังใน [README](../README.md) คือ Nginx · frontend · backend · database ช่วงเวลาของงานเว็บอยู่ใน [`ROADMAP.md`](ROADMAP.md#-เว็บแอป--nginx--frontend--backend)

### เหตุผล

- ที่เรากำลังทำอยู่คือเว็บแอปที่ใช้งานได้จริง
- Nginx เป็นของที่เว็บก็ต้องใช้กันเพื่อความปลอดภัยระดับหนึ่งอยู่แล้ว

### ผลที่ตามมา

- ✅ ผู้ใช้ทั้ง 2 กลุ่มใช้ระบบผ่านเบราว์เซอร์ได้จริง
- ⚠️ มีงาน 3 ส่วนที่ไม่อยู่ในงานส่ง 4 ชิ้น ต้องแบ่งคนและเวลามาทำด้วย
- ⚠️ backend ต่อ database ได้หลังเลือก DBMS ([ADR-005](#adr-005--เลือก-dbms))

## ADR-009 — เลือกภาษาและวิธีรันเว็บแอป

**วันที่**: 12 พ.ย. 2026 · **สถานะ**: ⬜ ยังไม่ตกลง

### บริบท

งานเว็บแอปเริ่มพร้อมขั้น 2 ตาม [ADR-008](#adr-008--ทำเป็นเว็บแอปที่ใช้งานได้จริง) แต่กลุ่มยังไม่ได้คุยว่า frontend กับ backend เขียนด้วยภาษาอะไร และทุกคนจะรันระบบทั้ง 4 ส่วนในเครื่องตัวเองยังไง

### ที่รู้ตอนนี้

- ระบบมี 4 ส่วนตาม [ADR-008](#adr-008--ทำเป็นเว็บแอปที่ใช้งานได้จริง) คือ Nginx · frontend · backend · database
- งานส่ง 4 ชิ้นของอาจารย์ไม่มีหน้าเว็บหรือ API สไลด์หน้า 11 จึงไม่ได้กำหนดภาษา
- DBMS คือ PostgreSQL ([ADR-005](#adr-005--เลือก-dbms))
- ประชุมครั้งที่ 1 (13 พ.ย.) ตกลงว่า **database กับเว็บอยู่คนละเครื่อง** (2 เครื่อง) ส่วนภาษายังไม่ได้เลือก

### สิ่งที่ต้องทำก่อนตัดสิน

- ตกลงภาษาของ frontend และ backend (ยังไม่กำหนดวัน · ต้องได้ก่อน backend ต่อ database ในรอบ 5)
- ตกลงวิธีรันทั้ง 4 ส่วนในเครื่องของทุกคน
- เลือกแล้วเขียนวิธีติดตั้งและรันไว้ใน repo ก่อนเริ่มเขียนโค้ด แบบไฟล์ [`INSTALL.md`](https://github.com/boss2912/luma-webapp-g04/blob/main/INSTALL.md) ของ luma-webapp-g04

## ADR-010 — บ้านหนึ่งมีบัญชีเดียว ทุกคนในบ้านใช้ร่วมกัน

**วันที่**: 13 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ประชุมครั้งที่ 1 ตกลงว่า 1 คนอยู่ได้บ้านเดียว แต่ยังไม่ได้ตกลงว่าใครสร้างบ้าน และคนในบ้านเข้าระบบยังไง

### การตัดสินใจ

เจ้าของบ้าน 1 คนสมัครบัญชีบ้าน (ชื่อบ้านสำหรับล็อกอินห้ามซ้ำกับบ้านอื่น) แล้วทุกคนในบ้านใช้บัญชีนี้ล็อกอินจากโทรศัพท์หรือคอมของตัวเอง ผู้ดูแลระบบใช้บัญชีแยก

### ผลที่ตามมา

- ✅ ไม่ต้องมีขั้นเชิญหรือรับสมาชิกเข้าบ้าน
- ⚠️ ระบบรู้แค่ว่า **บ้านไหน** ทำอาหารหรือทิ้งของ ไม่รู้ว่าใครในบ้านเป็นคนทำ
- ⚠️ proposal ข้อ 6 ที่ส่งไปแล้วมี "ข้อมูลสมาชิก" ต้องตกลงว่ายังเก็บไว้ไหม ([กฎของระบบ ข้อ 4](../design/business-rules.md#4-ยังไม่ตกลง-ต้องปิดในรอบที่-1))

## ADR-011 — วัตถุดิบมีธง "ของติดบ้าน"

**วันที่**: 13 พ.ย. 2026 (ประชุมครั้งที่ 1) · **สถานะ**: ✅

### บริบท

ไม่มีใครบันทึกเกลือ น้ำมัน น้ำปลา เข้าตู้ แต่สูตรเกือบทุกสูตรใช้ ทดลองกับข้อมูลตัวอย่างแล้ว ถ้าไม่มีธง ระบบแนะนำเมนูได้ 0 จาก 5 เมนู ถ้ามีธงได้ 3 จาก 5

### การตัดสินใจ

วัตถุดิบมีธง "ของติดบ้าน" ระบบถือว่าของที่มีธงนี้มีอยู่แล้วตอนแนะนำเมนู

### ผลที่ตามมา

- ✅ แนะนำเมนูได้จริงโดยไม่ต้องบันทึกเครื่องปรุงทุกขวด
- ⚠️ ยังไม่ตกลง: ธงติดที่วัตถุดิบกลาง หรือแต่ละบ้านตั้งเอง · ของติดบ้านหักตอนทำอาหารไหม ([กฎของระบบ ข้อ 2.2](../design/business-rules.md#22-หมวดหมู่และวัตถุดิบ))

## ADR-012 — เก็บว่าทำอาหารแต่ละครั้งหักล็อตไหนไปเท่าไร

**วันที่**: 13 พ.ย. 2026 (ประชุมครั้งที่ 1) · **สถานะ**: ✅

### บริบท

ทำอาหาร 1 ครั้งหักได้หลายล็อตตาม [ADR-001](#adr-001--ทำอาหารแล้วระบบหักวัตถุดิบตามสูตร) ถ้าเก็บแค่ว่าทำสูตรไหน แล้วผู้ดูแลระบบแก้สูตรทีหลัง ประวัติเก่าจะคำนวณย้อนไม่ได้ว่าหักอะไรไป

### การตัดสินใจ

ทำอาหารแต่ละครั้ง เก็บว่าหักล็อตไหนไปเท่าไร ในธุรกรรมเดียวกับการหัก (แบบเดียวกับตัวอย่างหน้า 30 ที่เก็บราคา ณ ตอนซื้อ)

### ผลที่ตามมา

- ✅ ประวัติไม่เปลี่ยนตามสูตรที่ถูกแก้
- ✅ ยกเลิกการทำอาหารที่กดผิดได้ โดยคืนของเข้าล็อตเดิมตามที่เก็บไว้
- ⚠️ มีตารางเพิ่ม 1 ตาราง (การทำอาหาร ↔ ล็อต)

## ADR-013 — ไฟล์ ER เก็บทั้ง .drawio และ .drawio.png

**วันที่**: 13 พ.ย. 2026 (ประชุมครั้งที่ 1) · **สถานะ**: ✅

### บริบท

ร่างเดิมเสนอ `.drawio.png` ไฟล์เดียว ที่ประชุมเลือกเก็บทั้งสองแบบ และวาดแบบไฟล์ตัวอย่างของวิชาสัปดาห์ที่ 1

### การตัดสินใจ

- เก็บ `er-diagram.drawio` (ไฟล์ต้นฉบับ) และ `er-diagram.drawio.png` (รูปที่เปิดดูบน GitHub ได้) ใน [`../design/`](../design/) แก้ทีละคน
- วาดแบบเดียวกับตัวอย่างสัปดาห์ที่ 1: entity เป็นตาราง มีช่อง PK / FK หน้าชื่อ attribute · ชื่อเป็นภาษาอังกฤษตัวเล็กคั่นด้วย `_` · เส้นความสัมพันธ์แบบ crow's foot

### ผลที่ตามมา

- ✅ เปิดดูรูปบน GitHub ได้ และมีไฟล์ต้นฉบับแก้ต่อ
- ⚠️ ทุกครั้งที่แก้ `.drawio` ต้อง export `.drawio.png` ใหม่ใน PR เดียวกัน ไม่งั้นสองไฟล์จะไม่ตรงกัน
