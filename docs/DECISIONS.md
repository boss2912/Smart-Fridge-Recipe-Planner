# DECISIONS — บันทึกการตัดสินใจของโปรเจกต์ (ADR)

> **ADR = Architecture Decision Record** — บันทึกว่า "ตัดสินใจอะไร ตอนไหน เพราะอะไร"
> schema กับ SQL บอกได้แค่ว่า *ทำอะไร* แต่บอกไม่ได้ว่า *ทำไมไม่ทำอีกแบบ*

ก่อนแก้อะไรที่มี ADR อยู่ ให้อ่าน ADR นั้นก่อน
ถ้าคิดว่าการตัดสินใจเดิมผิด ไม่ต้องลบของเดิม ให้เพิ่ม ADR ใหม่ที่เขียนว่า "แทนที่ ADR-00X" แล้วเปลี่ยนสถานะของอันเก่าเป็น 🔁

## ADR-001 — ทำอาหารแล้วระบบหักวัตถุดิบตามสูตร

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ร่างแรกของ proposal ให้สมาชิกบันทึกได้ว่าทำเมนูอะไร แต่จำนวนของในตู้ไม่ลดลง ทางแก้มีสองทาง คือให้ระบบหักตามสูตรเอง หรือให้สมาชิกไปแก้จำนวนเอง

### ปัญหาที่เกิดถ้าไม่หัก

จำนวนในตู้จะไม่ลดลงเลย บ้านที่ทำไข่เจียวไปหลายครั้งจนไข่หมด ระบบก็ยังเห็นไข่เท่าเดิม และยังแนะนำไข่เจียวต่อ ส่วนทางที่ให้สมาชิกแก้เอง ตัวเลขจะถูกก็ต่อเมื่อทุกคนจำได้ทุกครั้ง

### การตัดสินใจ

สมาชิกบันทึกแค่ว่าทำเมนูไหน แล้วระบบหักวัตถุดิบตามปริมาณในสูตรเอง

- หักเฉพาะล็อตในตู้บ้านตัวเองที่ยังไม่หมดอายุ โดยหักจากล็อตที่หมดอายุเร็วที่สุดก่อน
- เช็คก่อนว่าวัตถุดิบทุกอย่างในสูตรพอ (นับเฉพาะล็อตแบบข้อบน) ถ้าอย่างใดอย่างหนึ่งไม่พอ ไม่บันทึกอะไรเลยทั้งรายการ
- การบันทึกประวัติการทำอาหารกับการหักของ อยู่ในธุรกรรม (transaction) เดียวกัน

### ผลที่ตามมา

- ✅ จำนวนในตู้ตรงกับของจริงโดยไม่ต้องมีใครจำ
- ⚠️ SQL ในขั้น 3 ซับซ้อนขึ้น เพราะต้องหักหลายแถวในคราวเดียว
- ⚠️ คำสั่งที่หักไล่ทีละล็อต ถ้าของไม่พอจะหักเท่าที่มีโดยไม่แจ้ง error ขั้นเช็คก่อนหักจึงตัดทิ้งไม่ได้

## ADR-002 — รายการซื้อของกับราคาไม่อยู่ในขอบเขต

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ระหว่างร่าง proposal เคยมีฉบับที่ส่งของขาดเข้ารายการซื้อของ และเก็บราคาไว้คิดค่าใช้จ่าย

### การตัดสินใจ

ตัดรายการซื้อของกับราคาออกจากขอบเขต

### ผลที่ตามมา

- ✅ ข้อมูลหลักเหลือ 8 อย่าง ขอบเขตพอดีกับโครงงานกลุ่ม
- ⚠️ เอกสารและการนำเสนอห้ามอ้างว่าระบบช่วย "ลดค่าใช้จ่าย" เพราะไม่มีข้อมูลราคาให้พิสูจน์

## ADR-003 — ต้องมีการบันทึกการทิ้งของ

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ของในตู้ออกได้สองทาง คือใช้ทำอาหาร กับทิ้งเพราะหมดอายุหรือเสีย ถ้าบันทึกได้แต่ทางแรก ของที่ทิ้งไปแล้วจะยังค้างอยู่ในตัวเลข

### การตัดสินใจ

สมาชิกบันทึกว่าทิ้งของจากล็อตไหน จำนวนเท่าไร แล้วระบบหักออกจากล็อตนั้น และเก็บเป็นประวัติการทิ้ง (ล็อต / จำนวน / วันที่ทิ้ง)

- ทิ้งเกินกว่าที่ล็อตเหลืออยู่ไม่ได้
- ทิ้งได้เฉพาะของในตู้บ้านตัวเอง
- ล็อตที่ทิ้งหมดแล้วไม่ลบออก ประวัติการทิ้งจะได้ยังอ้างถึงได้
- การบันทึกประวัติการทิ้งกับการหักจากล็อต อยู่ในธุรกรรม (transaction) เดียวกัน

### ผลที่ตามมา

- ✅ จำนวนในตู้ = ของที่ซื้อ − ของที่ใช้ทำอาหาร − ของที่ทิ้ง
- ✅ ดูย้อนหลังได้ว่าบ้านไหนทิ้งอะไรไปเท่าไร
- ⚠️ ข้อมูลหลักเพิ่มเป็น 8 อย่าง

## ADR-004 — วัตถุดิบหนึ่งอย่างใช้หน่วยมาตรฐานเดียว

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ระบบต้องเทียบปริมาณในสูตรกับจำนวนในตู้ ถ้าบ้านหนึ่งบันทึกไข่เป็น "1 แผง" แต่สูตรใช้ "2 ฟอง" ระบบจะเทียบ 1 กับ 2 แล้วสรุปว่าไข่ไม่พอ ทั้งที่จริงมี 30 ฟอง

### การตัดสินใจ

วัตถุดิบแต่ละอย่างมีหน่วยมาตรฐานเดียว เก็บไว้ที่ข้อมูลวัตถุดิบ ทั้งล็อตในตู้และปริมาณในสูตรใช้หน่วยนี้ ระบบจึงไม่ต้องแปลงหน่วย

### ผลที่ตามมา

- ✅ query เทียบปริมาณได้ตรงๆ
- ⚠️ ตอนบันทึกของเข้าตู้ต้องกรอกเป็นหน่วยมาตรฐาน เช่น ไข่ 1 แผงต้องกรอกเป็น 30 ฟอง

## ADR-005 — เลือก DBMS

**วันที่**: 11 พ.ย. 2026 · ตัดสิน 13 พ.ย. 2026 (ประชุมครั้งที่ 1) · **สถานะ**: ✅

### บริบท

ขั้น 3 ต้องเขียน SQL จริง ไวยากรณ์บางส่วนต่างกันในแต่ละ DBMS เช่น ฟังก์ชันวันที่ จึงต้องเลือกก่อนเขียนไฟล์ SQL

### ที่รู้ตอนเลือก

- สไลด์หน้า 9 ยกตัวอย่าง DBMS 4 ตัว คือ MySQL, PostgreSQL, Oracle, SQL Server
- สไลด์ไม่ได้บอกว่าโครงงานต้องใช้ตัวไหน กลุ่มเลือกเองได้

### การตัดสินใจ

ใช้ **PostgreSQL** ไฟล์ SQL ทุกไฟล์ใน [`../database/`](../database/) เขียนตามไวยากรณ์ของ PostgreSQL

### ผลที่ตามมา

- ✅ เริ่มเขียนไฟล์ SQL ได้ ไม่ต้องรอเลือกแล้ว
- ⚠️ ทุกคนต้องติดตั้ง PostgreSQL หรือต่อเครื่อง database เดียวกันได้ วิธีรันอยู่ใน [ADR-009](#adr-009--เลือกภาษาและวิธีรันเว็บแอป)

## ADR-006 — รายชื่อสมาชิกไม่ขึ้น repo สาธารณะ

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: 🔁 ถูกแทนที่ด้วย [ADR-007](#adr-007--รายชื่อสมาชิกและรหัสนักศึกษาขึ้น-readme)

### บริบท

repo นี้เป็นสาธารณะ ใครก็เปิดดูได้ ส่วนแบบฟอร์มของอาจารย์ต้องใส่ชื่อ นามสกุล รหัสนักศึกษา และอีเมลของสมาชิก

### การตัดสินใจ

ชื่อ นามสกุล รหัสนักศึกษา และอีเมลของสมาชิก ใส่เฉพาะในแบบฟอร์มที่ส่งอาจารย์ ไม่ใส่ในไฟล์ใดของ repo เอกสารใน repo เรียกสมาชิกว่า "คนที่ 1–6"

### บังคับใช้อย่างไร

[แม่แบบ PR](../.github/pull_request_template.md) มีข้อนี้ใน checklist คนรีวิวต้องตรวจก่อน approve

## ADR-007 — รายชื่อสมาชิกและรหัสนักศึกษาขึ้น README

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅ · แทนที่ [ADR-006](#adr-006--รายชื่อสมาชิกไม่ขึ้น-repo-สาธารณะ)

### บริบท

ADR-006 ไม่ใส่รายชื่อสมาชิกใน repo เพราะ repo เป็นสาธารณะ ต่อมาเปลี่ยนให้หัวข้อทีมใน README บอกได้ว่าใครอยู่ในทีม

### การตัดสินใจ

หัวข้อทีมใน [README](../README.md#-ทีม-7-คน) ใส่ชื่อ นามสกุล และรหัสนักศึกษาของสมาชิกทั้ง 7 คน ส่วนอีเมลของสมาชิกใส่เฉพาะในแบบฟอร์มที่ส่งอาจารย์ ไม่ใส่ใน repo

### ผลที่ตามมา

- ✅ คนที่เปิด repo รู้ว่าใครอยู่ในทีม
- ⚠️ repo เป็นสาธารณะ ใครเปิดก็เห็นชื่อกับรหัสนักศึกษา และถึงจะลบออกทีหลัง ประวัติ commit ก็ยังเก็บไว้

## ADR-008 — ทำเป็นเว็บแอปที่ใช้งานได้จริง

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

งานส่ง 4 ชิ้นของอาจารย์ (Lecture 1 หน้า 11) เป็นงานออกแบบและสร้างฐานข้อมูล ไม่มีหน้าเว็บหรือ API

### การตัดสินใจ

ระบบมี 4 ส่วนตามผังใน [README](../README.md) คือ Nginx · frontend · backend · database ช่วงเวลาของงานเว็บอยู่ใน [`ROADMAP.md`](ROADMAP.md#-เว็บแอป--nginx--frontend--backend)

### เหตุผล

- ที่เรากำลังทำอยู่คือเว็บแอปที่ใช้งานได้จริง
- Nginx เป็นของที่เว็บก็ต้องใช้กันเพื่อความปลอดภัยระดับหนึ่งอยู่แล้ว

### ผลที่ตามมา

- ✅ ผู้ใช้ทั้ง 2 กลุ่มใช้ระบบผ่านเบราว์เซอร์ได้จริง
- ⚠️ มีงาน 3 ส่วนที่ไม่อยู่ในงานส่ง 4 ชิ้น ต้องแบ่งคนและเวลามาทำด้วย
- ⚠️ backend ต่อ database ได้หลังเลือก DBMS ([ADR-005](#adr-005--เลือก-dbms))

## ADR-009 — เลือกภาษาและวิธีรันเว็บแอป

**วันที่**: 12 พ.ย. 2026 · ตัดสิน 13 พ.ย. 2026 (บอสตัดสินหลังประชุม) · **สถานะ**: ✅

### บริบท

งานเว็บแอปเริ่มพร้อมขั้น 2 ตาม [ADR-008](#adr-008--ทำเป็นเว็บแอปที่ใช้งานได้จริง) แต่กลุ่มยังไม่ได้คุยว่า frontend กับ backend เขียนด้วยภาษาอะไร และทุกคนจะรันระบบทั้ง 4 ส่วนในเครื่องตัวเองยังไง

### การตัดสินใจ

**ภาษา**

- backend: **Python + Flask**
- frontend: **HTML + CSS** เขียนเป็น template ที่ Flask เติมข้อมูลแล้วส่งให้เบราว์เซอร์ · ใช้ **JavaScript เฉพาะที่จำเป็น** เช่น ตะกร้าบันทึกของเข้าตู้ กับส่วนเลือกเครื่องปรุงตอนทำเมนู ([ADR-014](#adr-014--เครื่องปรุงลงตู้เป็นล็อต-เลือกเพิ่มตอนทำอาหาร))

**เดโมวันนำเสนอ 2 เครื่อง**

- เครื่อง 1: **Nginx** ส่งไฟล์ CSS / JS / รูป เอง และส่งต่อคำขออื่นไปที่เครื่อง 2
- เครื่อง 2: **Flask** (สร้างหน้า HTML) + **PostgreSQL**
- แทนมติประชุมครั้งที่ 1 ที่ให้ database อยู่คนละเครื่องกับเว็บ

**ตอนพัฒนาในเครื่องตัวเอง**

- แต่ละคนติดตั้ง Python กับ PostgreSQL เอง แล้วรัน Flask ตรงๆ ไม่ผ่าน Nginx
- วิธีติดตั้งและรันเขียนไว้ใน repo ก่อนเริ่มเขียนโค้ด แบบไฟล์ [`INSTALL.md`](https://github.com/boss2912/luma-webapp-g04/blob/main/INSTALL.md) ของ luma-webapp-g04

### เหตุผล

- เขียน Python ทั้งฝั่งที่สร้างหน้าเว็บและฝั่งที่ต่อ database ไม่ต้องเขียนหน้าเว็บทั้งหน้าด้วย JavaScript
- งานส่วนใหญ่ของระบบ (บันทึกของเข้าตู้ · ทิ้งของ · ดูประวัติ) เป็นการกรอกฟอร์มแล้วโหลดหน้าใหม่ ไม่ต้องอัปเดตสด

### ผลที่ตามมา

- ✅ frontend กับ backend รันเป็นโปรแกรม Flask ตัวเดียว ไม่ต้องตกลงรูปแบบ API แยก
- ⚠️ frontend ดูแล template / CSS / JavaScript ใน [`../frontend/`](../frontend/) · backend ดูแล route ล็อกอิน สิทธิ์ และ query ใน [`../backend/`](../backend/) · ต้องตกลงกันว่าแต่ละหน้าได้ข้อมูลอะไรจาก route ([จุดที่ต้องคุยกันก่อนลงมือ ข้อ 6](TEAM_AND_WORKFLOW.md#จุดที่ต้องคุยกันก่อนลงมือ))
- ⚠️ ทุกคนลง Python กับ PostgreSQL เอง เวอร์ชันอาจไม่ตรงกัน วิธีติดตั้งต้องระบุเวอร์ชัน
- ⚠️ ตอนพัฒนาไม่ผ่าน Nginx ต้องทดสอบแบบ 2 เครื่องผ่าน Nginx ก่อนวันนำเสนอ ([ROADMAP รอบ 7](ROADMAP.md#-ปฏิทิน-9-รอบ-พุธ--อังคาร))

## ADR-010 — บ้านหนึ่งมีบัญชีเดียว ทุกคนในบ้านใช้ร่วมกัน

**วันที่**: 13 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ประชุมครั้งที่ 1 ตกลงว่า 1 คนอยู่ได้บ้านเดียว แต่ยังไม่ได้ตกลงว่าใครสร้างบ้าน และคนในบ้านเข้าระบบยังไง

### การตัดสินใจ

เจ้าของบ้าน 1 คนสมัครบัญชีบ้าน (ชื่อบ้านสำหรับล็อกอินห้ามซ้ำกับบ้านอื่น) แล้วทุกคนในบ้านใช้บัญชีนี้ล็อกอินจากโทรศัพท์หรือคอมของตัวเอง ผู้ดูแลระบบใช้บัญชีแยก ([ADR-015](#adr-015--ผู้ดูแลระบบดูได้ทุกบ้านและปิดบัญชีบ้านได้))

### ผลที่ตามมา

- ✅ ไม่ต้องมีขั้นเชิญหรือรับสมาชิกเข้าบ้าน
- ⚠️ ระบบรู้แค่ว่า **บ้านไหน** ทำอาหารหรือทิ้งของ ไม่รู้ว่าใครในบ้านเป็นคนทำ
- ✅ ไม่เก็บข้อมูลสมาชิก ประวัติการทำอาหารและการทิ้งเป็นของบ้านรวมกัน (13 พ.ย. บอสตัดสิน) ข้อมูลสมาชิกจึงไม่อยู่ในข้อมูลหลัก
- ⚠️ ต่างจาก proposal ข้อ 5–6 ที่ส่งไปแล้ว ซึ่งเขียนว่ามี "ข้อมูลสมาชิก" · [`proposal.md`](proposal.md) ไม่แก้ เพราะเป็นฉบับที่ส่งไปแล้ว

## ADR-011 — วัตถุดิบมีธง "ของติดบ้าน"

**วันที่**: 13 พ.ย. 2026 (ประชุมครั้งที่ 1) · **สถานะ**: 🔁 ถูกแทนที่ด้วย [ADR-014](#adr-014--เครื่องปรุงลงตู้เป็นล็อต-เลือกเพิ่มตอนทำอาหาร)

### บริบท

ไม่มีใครบันทึกเกลือ น้ำมัน น้ำปลา เข้าตู้ แต่สูตรเกือบทุกสูตรใช้ ทดลองกับข้อมูลตัวอย่างแล้ว ถ้าไม่มีธง ระบบแนะนำเมนูได้ 0 จาก 5 เมนู ถ้ามีธงได้ 3 จาก 5

### การตัดสินใจ

วัตถุดิบมีธง "ของติดบ้าน" ระบบถือว่าของที่มีธงนี้มีอยู่แล้วตอนแนะนำเมนู

### ผลที่ตามมา

- ✅ แนะนำเมนูได้จริงโดยไม่ต้องบันทึกเครื่องปรุงทุกขวด
- ⚠️ ยังไม่ตกลง: ธงติดที่วัตถุดิบกลาง หรือแต่ละบ้านตั้งเอง · ของติดบ้านหักตอนทำอาหารไหม ([กฎของระบบ ข้อ 2.3](../design/business-rules.md#23-หมวดหมู่และวัตถุดิบ))

## ADR-014 — เครื่องปรุงลงตู้เป็นล็อต เลือกเพิ่มตอนทำอาหาร

**วันที่**: 13 พ.ย. 2026 (บอสตัดสินหลังประชุมครั้งที่ 1) · **สถานะ**: ✅ · แทนที่ [ADR-011](#adr-011--วัตถุดิบมีธง-ของติดบ้าน)

### บริบท

ADR-011 ให้วัตถุดิบมีธง "ของติดบ้าน" ระบบถือว่ามีเสมอ แต่ยังไม่ตกลงว่าธงติดที่วัตถุดิบกลางหรือแต่ละบ้านตั้งเอง และหักตอนทำอาหารไหม

### การตัดสินใจ

- ไม่มีธง "ของติดบ้าน" · เครื่องปรุง (วัตถุดิบหมวด "เครื่องปรุง") ซื้อมาก็บันทึกเข้าตู้เป็นล็อตเหมือนของอื่น
- สูตรใส่วัตถุดิบที่ต้องใช้ครบทุกอย่าง รวมเครื่องปรุงที่สูตรนั้นต้องใช้
- หน้าทำเมนูแสดงวิธีทำ ด้านล่างมีส่วน "เครื่องปรุงเพิ่มเติม" สำหรับใส่เพิ่มจากสูตร: เลือกเครื่องปรุง ใส่จำนวนเป็นตัวเลขในหน่วยมาตรฐาน (ใส่แบบประมาณได้) หรือกด "ไม่มีเพิ่มเติม"
- **เครื่องปรุงไม่พอ ไม่ทำให้ทำอาหารไม่ได้** (ข้อยกเว้นของ [ADR-001](#adr-001--ทำอาหารแล้วระบบหักวัตถุดิบตามสูตร) ซึ่งยังใช้กับวัตถุดิบหมวดอื่น)
  - แนะนำเมนู: วัตถุดิบหมวดอื่นพอ แต่เครื่องปรุงไม่พอ เมนูยังขึ้น พร้อมป้าย "เครื่องปรุงไม่พอ"
  - ทำอาหาร: หักเครื่องปรุงเท่าที่มีในล็อต ทั้งที่อยู่ในสูตรและที่เพิ่มเติม
- หักเครื่องปรุงในธุรกรรมเดียวกับการทำอาหาร และเก็บว่าหักล็อตไหนไปเท่าไร ([ADR-012](#adr-012--เก็บว่าทำอาหารแต่ละครั้งหักล็อตไหนไปเท่าไร))

### เหตุผล

- ใส่เครื่องปรุงเท่าไรขึ้นกับคนทำแต่ละครั้ง ตวงเป๊ะไม่ได้ จึงให้คนทำใส่เองตอนทำ

### ผลที่ตามมา

- ✅ ไม่ต้องมีธง และไม่ต้องมีตารางตั้งค่าแยกต่อบ้าน
- ✅ จำนวนเครื่องปรุงในตู้ลดลงตามที่ใช้จริง
- ⚠️ query แนะนำเมนูกับการทำอาหารต้องแยกเครื่องปรุงออกจากวัตถุดิบอื่นด้วยหมวดหมู่ "เครื่องปรุง" หมวดนี้ห้ามแก้ชื่อหรือลบ
- ⚠️ บ้านที่ไม่ได้บันทึกเครื่องปรุงเข้าตู้ จะเห็นป้าย "เครื่องปรุงไม่พอ" ที่เมนูซึ่งใช้เครื่องปรุงนั้น

## ADR-015 — ผู้ดูแลระบบดูได้ทุกบ้านและปิดบัญชีบ้านได้

**วันที่**: 13 พ.ย. 2026 (บอสตัดสินหลังประชุมครั้งที่ 1) · **สถานะ**: ✅

### บริบท

[ADR-010](#adr-010--บ้านหนึ่งมีบัญชีเดียว-ทุกคนในบ้านใช้ร่วมกัน) ให้ผู้ดูแลระบบมีบัญชีแยก แต่ยังไม่ได้บอกว่าทำอะไรได้บ้าง ส่วนล็อตกับประวัติห้ามลบ ([ADR-003](#adr-003--ต้องมีการบันทึกการทิ้งของ))

### การตัดสินใจ

- ผู้ดูแลระบบมีบัญชีแยก เก็บเป็นข้อมูลบัญชีผู้ดูแลระบบของตัวเอง ไม่สังกัดบ้าน
- ทำได้ 3 อย่าง:
  - **ดู** รายชื่อบ้านทุกบ้าน และของในตู้ของบ้านไหนก็ได้ ดูอย่างเดียว แก้หรือทิ้งแทนบ้านไม่ได้
  - **ปิดบัญชีบ้าน** (= "ลบ"): บ้านนั้นล็อกอินไม่ได้และไม่แสดงในรายชื่อ แต่ล็อตกับประวัติยังอยู่ · เปิดคืนได้ · ชื่อบ้านสำหรับล็อกอินห้ามซ้ำแม้บัญชีปิดแล้ว
  - **ดูภาพรวมทุกบ้าน (dashboard)** เช่น เติมล็อตเข้าตู้วันไหนของสัปดาห์ · ทำอาหารกี่ครั้งต่อสัปดาห์
- ผู้ดูแลระบบไม่ได้ดูแลรายการวัตถุดิบและสูตร บ้านเพิ่มเอง ([ADR-016](#adr-016--บ้านเพิ่มวัตถุดิบและสูตรของตัวเอง))

### ผลที่ตามมา

- ✅ ยอดทิ้งต่อบ้านกับเมนูที่ทำบ่อยยังนับข้อมูลเก่าครบ
- ⚠️ ข้อมูลหลักเพิ่มบัญชีผู้ดูแลระบบ รวมเป็น 8 อย่าง
- ⚠️ ตารางบ้านเพิ่มช่องสถานะบัญชี (ใช้งาน / ปิด) และล็อกอินต้องเช็คช่องนี้
- ⚠️ backend ต้องแยกสิทธิ์ให้ชัด: บ้านเห็นเฉพาะของตัวเอง ผู้ดูแลระบบเห็นทุกบ้านแต่แก้ไม่ได้
- ⚠️ ต่างจาก proposal ข้อ 4–5 ที่ส่งไปแล้ว ซึ่งเขียนว่าผู้ดูแลระบบดูแลรายการวัตถุดิบและสูตรอาหารกลาง

## ADR-016 — บ้านเพิ่มวัตถุดิบและสูตรของตัวเอง

**วันที่**: 13 พ.ย. 2026 (บอสตัดสินหลังประชุมครั้งที่ 1) · **สถานะ**: ✅

### บริบท

เดิมผู้ดูแลระบบเป็นคนเพิ่มรายการวัตถุดิบกลางและสูตรกลางที่ทุกบ้านใช้ร่วมกัน บ้านที่ซื้อของที่ไม่มีในรายการจะบันทึกเข้าตู้ไม่ได้

### การตัดสินใจ

- แต่ละบ้านเพิ่มวัตถุดิบและสูตรของตัวเอง ใช้ได้เฉพาะบ้านนั้น บ้านอื่นไม่เห็น
- ชื่อวัตถุดิบห้ามซ้ำภายในบ้านเดียวกัน คนละบ้านมี "ไข่" ของตัวเองได้
- หมวดหมู่ (เนื้อ · ผัก · เครื่องปรุง · ไข่ · เครื่องดื่ม · อื่นๆ) เป็นชุดเดียวที่ระบบตั้งไว้ ทุกบ้านใช้ร่วมกัน

### ผลที่ตามมา

- ✅ ซื้ออะไรมาก็บันทึกเข้าตู้ได้
- ⚠️ ตารางวัตถุดิบและตารางสูตรมี FK ไปที่บ้าน · UNIQUE ของชื่อวัตถุดิบเป็น (บ้าน, ชื่อ)
- ⚠️ ล็อตกับวัตถุดิบ และสูตรกับวัตถุดิบในสูตร ต้องเป็นของบ้านเดียวกัน ต้องบังคับใน schema หรือ backend ([กฎของระบบ ข้อ 3](../design/business-rules.md#3-ความถูกต้องของข้อมูล-data-integrity--constraints))
- ⚠️ บ้านใหม่เริ่มจากไม่มีวัตถุดิบและสูตรเลย
- ⚠️ ต่างจาก proposal ที่ส่งไปแล้ว ซึ่งเขียนว่าวัตถุดิบและสูตรเป็นรายการกลางที่ผู้ดูแลระบบดูแล

## ADR-017 — ทำอาหารเลือกได้ว่าทำกี่เท่าของสูตร

### บริบท

สูตรเก็บปริมาณสำหรับทำครั้งเดียว แต่บางครั้งทำมากกว่านั้น

### การตัดสินใจ
