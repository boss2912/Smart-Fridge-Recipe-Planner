# DECISIONS — บันทึกการตัดสินใจของโปรเจกต์ (ADR)

> **ADR = Architecture Decision Record** — บันทึกว่า "ตัดสินใจอะไร ตอนไหน เพราะอะไร"
> schema กับ SQL บอกได้แค่ว่า *ทำอะไร* แต่บอกไม่ได้ว่า *ทำไมไม่ทำอีกแบบ*

ก่อนแก้อะไรที่มี ADR อยู่ ให้อ่าน ADR นั้นก่อน
ถ้าคิดว่าการตัดสินใจเดิมผิด ไม่ต้องลบของเดิม ให้เพิ่ม ADR ใหม่ที่เขียนว่า "แทนที่ ADR-00X" แล้วเปลี่ยนสถานะของอันเก่าเป็น 🔁

## ADR-001 — ทำอาหารแล้วระบบหักวัตถุดิบตามสูตร

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ร่างแรกของ proposal ให้สมาชิกบันทึกได้ว่าทำเมนูอะไร แต่จำนวนของในตู้ไม่ลดลง ทางแก้มีสองทาง คือให้ระบบหักตามสูตรเอง หรือให้สมาชิกไปแก้จำนวนเอง

### ปัญหาที่เกิดถ้าไม่หัก

จำนวนในตู้จะไม่ลดลงเลย บ้านที่ทำไข่เจียวไปหลายครั้งจนไข่หมด ระบบก็ยังเห็นไข่เท่าเดิม และยังแนะนำไข่เจียวต่อ ส่วนทางที่ให้สมาชิกแก้เอง ตัวเลขจะถูกก็ต่อเมื่อทุกคนจำได้ทุกครั้ง

### การตัดสินใจ

สมาชิกบันทึกแค่ว่าทำเมนูไหน แล้วระบบหักวัตถุดิบตามปริมาณในสูตรเอง

- หักจากล็อตที่หมดอายุก่อนก่อน
- เช็คก่อนว่าวัตถุดิบทุกอย่างในสูตรพอ ถ้าอย่างใดอย่างหนึ่งไม่พอ ไม่บันทึกอะไรเลยทั้งรายการ
- การบันทึกประวัติการทำอาหารกับการหักของ อยู่ในธุรกรรม (transaction) เดียวกัน

### ผลที่ตามมา

- ✅ จำนวนในตู้ตรงกับของจริงโดยไม่ต้องมีใครจำ
- ⚠️ SQL ในขั้น 3 ซับซ้อนขึ้น เพราะต้องหักหลายแถวในคราวเดียว
- ⚠️ คำสั่งที่หักไล่ทีละล็อต ถ้าของไม่พอจะหักเท่าที่มีโดยไม่แจ้ง error ขั้นเช็คก่อนหักจึงตัดทิ้งไม่ได้

## ADR-002 — รายการซื้อของกับราคาไม่อยู่ในขอบเขต

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ระหว่างร่าง proposal เคยมีฉบับที่ส่งของขาดเข้ารายการซื้อของ และเก็บราคาไว้คิดค่าใช้จ่าย

### การตัดสินใจ

ตัดรายการซื้อของกับราคาออกจากขอบเขต

### ผลที่ตามมา

- ✅ ข้อมูลหลักเหลือ 8 อย่าง ขอบเขตพอดีกับโครงงานกลุ่ม
- ⚠️ เอกสารและการนำเสนอห้ามอ้างว่าระบบช่วย "ลดค่าใช้จ่าย" เพราะไม่มีข้อมูลราคาให้พิสูจน์

## ADR-003 — ต้องมีการบันทึกการทิ้งของ

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ของในตู้ออกได้สองทาง คือใช้ทำอาหาร กับทิ้งเพราะหมดอายุหรือเสีย ถ้าบันทึกได้แต่ทางแรก ของที่ทิ้งไปแล้วจะยังค้างอยู่ในตัวเลข

### การตัดสินใจ

สมาชิกบันทึกว่าทิ้งของจากล็อตไหน จำนวนเท่าไร แล้วระบบหักออกจากล็อตนั้น และเก็บเป็นประวัติการทิ้ง (ล็อต / จำนวน / วันที่ทิ้ง)

- ทิ้งเกินกว่าที่ล็อตเหลืออยู่ไม่ได้
- ทิ้งได้เฉพาะของในตู้บ้านตัวเอง
- ล็อตที่ทิ้งหมดแล้วไม่ลบออก ประวัติการทิ้งจะได้ยังอ้างถึงได้

### ผลที่ตามมา

- ✅ จำนวนในตู้ = ของที่ซื้อ − ของที่ใช้ทำอาหาร − ของที่ทิ้ง
- ✅ ดูย้อนหลังได้ว่าบ้านไหนทิ้งอะไรไปเท่าไร
- ⚠️ ข้อมูลหลักเพิ่มเป็น 8 อย่าง

## ADR-004 — วัตถุดิบหนึ่งอย่างใช้หน่วยมาตรฐานเดียว

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

ระบบต้องเทียบปริมาณในสูตรกับจำนวนในตู้ ถ้าบ้านหนึ่งบันทึกไข่เป็น "1 แผง" แต่สูตรใช้ "2 ฟอง" ระบบจะเทียบ 1 กับ 2 แล้วสรุปว่าไข่ไม่พอ ทั้งที่จริงมี 30 ฟอง

### การตัดสินใจ

วัตถุดิบแต่ละอย่างมีหน่วยมาตรฐานเดียว เก็บไว้ที่ข้อมูลวัตถุดิบ ทั้งล็อตในตู้และปริมาณในสูตรใช้หน่วยนี้ ระบบจึงไม่ต้องแปลงหน่วย

### ผลที่ตามมา

- ✅ query เทียบปริมาณได้ตรงๆ
- ⚠️ ตอนบันทึกของเข้าตู้ต้องกรอกเป็นหน่วยมาตรฐาน เช่น ไข่ 1 แผงต้องกรอกเป็น 30 ฟอง

## ADR-005 — เลือก DBMS

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ⬜ ยังไม่ตกลง

### บริบท

ขั้น 3 ต้องเขียน SQL จริง กลุ่มยังไม่ได้คุยกันว่าจะใช้ SQLite หรือ MySQL

### ที่รู้ตอนนี้

- สไลด์หน้า 9 ยกตัวอย่าง DBMS 4 ตัว คือ MySQL, PostgreSQL, Oracle, SQL Server
- สไลด์ไม่ได้บอกว่าโครงงานต้องใช้ตัวไหน

### สิ่งที่ต้องทำก่อนตัดสิน

- ถามอาจารย์ว่ากำหนด DBMS ไหม
- เลือกแล้วค่อยใส่ไฟล์ SQL ลง [`../database/`](../database/) ก่อนหน้านั้นยังไม่ใส่ เพราะไวยากรณ์บางส่วนต่างกันในแต่ละตัว เช่น ฟังก์ชันวันที่

## ADR-006 — รายชื่อสมาชิกไม่ขึ้น repo สาธารณะ

**วันที่**: 11 พ.ย. 2026 · **สถานะ**: ✅

### บริบท

repo นี้เป็นสาธารณะ ใครก็เปิดดูได้ ส่วนแบบฟอร์มของอาจารย์ต้องใส่ชื่อ นามสกุล รหัสนักศึกษา และอีเมลของสมาชิก

### การตัดสินใจ

ชื่อ นามสกุล รหัสนักศึกษา และอีเมลของสมาชิก ใส่เฉพาะในแบบฟอร์มที่ส่งอาจารย์ ไม่ใส่ในไฟล์ใดของ repo เอกสารใน repo เรียกสมาชิกว่า "คนที่ 1–6"
