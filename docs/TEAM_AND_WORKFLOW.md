# การแบ่งงานและวิธีทำงานร่วมกัน

> ⬜ **ร่าง — กลุ่มยังไม่ได้ตกลง**
> ตกลงกันแล้วให้ลบกล่องนี้ แล้วแก้บรรทัด 👤 ของแต่ละงานให้ตรงกับที่ตกลงจริง

เอกสารนี้ตอบว่า **ใครรับผิดชอบอะไร** และ **ต้องคุยอะไรกันก่อนลงมือ**

## ทีมมี 7 คน

รายชื่ออยู่ที่[หัวข้อทีมใน README](../README.md#-ทีม-7-คน) · สไลด์หน้า 11–12 เขียนกลุ่มละ 6 คน อาจารย์แจ้งว่า 6–7 คนได้ ([ดูข้อกำหนด 2.1](COURSE_REQUIREMENTS.md#21-เป้าหมายและขนาดกลุ่ม))

แบ่งตามงานที่ต้องส่ง 4 ชิ้น (หน้า 11) และ 3 ส่วนของเว็บแอป ([ADR-008](DECISIONS.md#adr-008--ทำเป็นเว็บแอปที่ใช้งานได้จริง) · ภาษาและวิธีรันยังไม่ตกลง [ADR-009](DECISIONS.md#adr-009--เลือกภาษาและวิธีรันเว็บแอป)) ในงานที่ต้องส่ง ขั้น 2 กับขั้น 3 เป็นงานก้อนใหญ่ที่สุด จึงแบ่งขั้นละ 2 งาน

```text
ขั้น 1  Proposal              →  ประสานงาน + Proposal
ขั้น 2  ER + Schema           →  ER Diagram · Relational Schema + Normalization
ขั้น 3  SQL                   →  SQL สร้างตาราง + ข้อมูลตัวอย่าง · SQL query ตามกฎของระบบ
ขั้น 4  รายงาน + นำเสนอ       →  รายงาน + สไลด์นำเสนอ · ทุกคนเขียนส่วนของตัวเอง
เว็บแอป                      →  Nginx · frontend · backend
```

## ประสานงาน + Proposal

👤 ยังไม่ได้ตกลงว่าใครรับ

- ดูแลแบบฟอร์ม proposal และ [`proposal.md`](proposal.md)
- อัปเดต [`ROADMAP.md`](ROADMAP.md) กับสถานะใน README
- ถามอาจารย์เรื่องที่ยังไม่รู้ ([`COURSE_REQUIREMENTS.md`](COURSE_REQUIREMENTS.md#5-ยังไม่รู้--ต้องถามอาจารย์)) แล้วจดคำตอบลงเอกสาร

## ER Diagram

👤 ยังไม่ได้ตกลงว่าใครรับ

- เขียนกฎของระบบ (business rules) แบบตัวอย่างร้านเสื้อผ้า หน้า 28–31
- วาด ER Diagram ด้วย draw.io (หน้า 13) → [`../design/`](../design/)

## Relational Schema + Normalization

👤 ยังไม่ได้ตกลงว่าใครรับ

- แปลง ER เป็นตาราง กำหนด PK / FK
- ทำ Normalization พร้อมเหตุผลแต่ละขั้น → [`../design/`](../design/)

## SQL สร้างตาราง + ข้อมูลตัวอย่าง

👤 ยังไม่ได้ตกลงว่าใครรับ

- DDL พร้อม constraint (PK, FK, NOT NULL, UNIQUE, CHECK) → [`../database/`](../database/)
- ข้อมูลตัวอย่างที่มีทุกกรณีที่ query ต้องเจอ เช่น ล็อตหมดอายุ ล็อตที่ทิ้งหมดแล้ว ของไม่พอทำเมนู

## SQL query ตามกฎของระบบ

👤 ยังไม่ได้ตกลงว่าใครรับ

- query ที่ระบบต้องทำ: เตือนของใกล้หมดอายุ · แนะนำเมนู · หักของตอนทำอาหาร · บันทึกการทิ้ง → [`../database/`](../database/)
- ทำตาม [ADR-001](DECISIONS.md#adr-001--ทำอาหารแล้วระบบหักวัตถุดิบตามสูตร) และ [ADR-003](DECISIONS.md#adr-003--ต้องมีการบันทึกการทิ้งของ)

## frontend

## จุดที่ต้องคุยกันก่อนลงมือ

งานแต่ละชิ้นต่อกันตรงจุดเหล่านี้ — **ตกลงกันก่อนเริ่มงาน** ไม่ใช่ทำเสร็จแล้วค่อยมาปรับ

| # | ระหว่าง | ต้องตกลงอะไร |
|---|---|---|
| 1 | ER Diagram ↔ Relational Schema + Normalization | ชื่อ entity กับ attribute ที่ใช้ตรงกันทั้งใน ER และในตาราง |
| 2 | Relational Schema + Normalization ↔ SQL สร้างตาราง + ข้อมูลตัวอย่าง | ชื่อตาราง คอลัมน์ ชนิดข้อมูล PK / FK |
| 3 | SQL สร้างตาราง + ข้อมูลตัวอย่าง ↔ SQL query ตามกฎของระบบ | ข้อมูลตัวอย่างต้องมีกรณีที่ query แต่ละตัวต้องเจอ |
| 4 | SQL query ตามกฎของระบบ ↔ รายงาน + สไลด์นำเสนอ | ผล query ที่จะยกไปใส่รายงานและสไลด์ |
| 5 | ทุกคน | DBMS ที่จะใช้ ([ADR-005](DECISIONS.md#adr-005--เลือก-dbms)) |
| 6 | frontend ↔ backend | คำขอ `/api/` แต่ละอัน: ส่งข้อมูลอะไรไป และได้อะไรกลับ |
| 7 | backend ↔ database | query ที่ backend เรียกใช้ · ทำอาหารกับทิ้งของต้องจบในธุรกรรมเดียว ([ADR-001](DECISIONS.md#adr-001--ทำอาหารแล้วระบบหักวัตถุดิบตามสูตร) · [ADR-003](DECISIONS.md#adr-003--ต้องมีการบันทึกการทิ้งของ)) |

Git workflow กับกติกา PR → [`../CONTRIBUTING.md`](../CONTRIBUTING.md)
