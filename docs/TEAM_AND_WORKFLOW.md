## จุดที่ต้องคุยกันก่อนลงมือ

งานแต่ละชิ้นต่อกันตรงจุดเหล่านี้ — **ตกลงกันก่อนเริ่มงาน** ไม่ใช่ทำเสร็จแล้วค่อยมาปรับ

| # | ระหว่าง | ต้องตกลงอะไร |
|---|---|---|
| 1 | ER Diagram ↔ Relational Schema + Normalization | ชื่อ entity กับ attribute ที่ใช้ตรงกันทั้งใน ER และในตาราง |
| 2 | Relational Schema + Normalization ↔ SQL สร้างตาราง + ข้อมูลตัวอย่าง | ชื่อตาราง คอลัมน์ ชนิดข้อมูล PK / FK |
| 3 | SQL สร้างตาราง + ข้อมูลตัวอย่าง ↔ SQL query ตามกฎของระบบ | ข้อมูลตัวอย่างต้องมีกรณีที่ query แต่ละตัวต้องเจอ |
| 4 | SQL query ตามกฎของระบบ ↔ รายงาน + สไลด์นำเสนอ | ผล query ที่จะยกไปใส่รายงานและสไลด์ |
| 5 | ทุกคน | ✅ DBMS คือ PostgreSQL ([ADR-005](DECISIONS.md#adr-005--เลือก-dbms)) |
| 6 | frontend ↔ backend | คำขอ `/api/` แต่ละอัน: ส่งข้อมูลอะไรไป และได้อะไรกลับ |
| 7 | backend ↔ database | query ที่ backend เรียกใช้ · ทำอาหารกับทิ้งของต้องจบในธุรกรรมเดียว ([ADR-001](DECISIONS.md#adr-001--ทำอาหารแล้วระบบหักวัตถุดิบตามสูตร) · [ADR-003](DECISIONS.md#adr-003--ต้องมีการบันทึกการทิ้งของ)) |

## วิธีทำงาน (Agile)

ตกลงในประชุมครั้งที่ 1 · อาจารย์ไม่ให้ส่งงานระหว่างทาง ทีมจึงดูผลงานกันเองทุกวันพุธ งานที่หลุดจะเห็นภายในสัปดาห์เดียว

- **รอบละ 1 สัปดาห์** เริ่มวันพุธ จบวันอังคาร ปฏิทิน 9 รอบอยู่ใน [`ROADMAP.md`](ROADMAP.md#-ปฏิทิน-9-รอบ-พุธ--อังคาร)
- **บทบาท:** เจ้าของรายการงาน (Product Owner) = บอส · คนคุมจังหวะ (Scrum Master) = บอส · ทีมทำงาน = ทุกคน

| กิจกรรม | เมื่อไหร่ | ทำอะไร |
|---|---|---|
| ดูผลงาน (Sprint Review) | พุธ 15 นาที | เปิดของที่ merge เข้า develop แล้วให้ทุกคนดูของจริง · ให้คนที่ไม่ได้ทำงานชิ้นนั้นเป็นคนอธิบาย |
| ทบทวนวิธีทำงาน (Retrospective) | พุธ ต่อกัน 10 นาที | อะไรดีทำต่อ · อะไรต้องเลิก · รอบหน้าลองอะไร |
| วางงานรอบใหม่ (Sprint Planning) | พุธ ต่อกัน 20 นาที | เลือกงานจากรายการเข้ารอบ แต่ละคนรับงานของตัวเอง |
| รายงานรายวัน (Daily) | ทุกวัน ก่อน 22.00 น. ในไลน์กลุ่ม | 3 บรรทัด: ทำอะไรไป · จะทำอะไร · ติดอะไร |

### เก็บงานไว้ที่ไหน

- รายการงานทั้งหมด = issue บน GitHub ใช้แม่แบบ "งาน" งานละ 1–2 วัน
- งานของรอบนี้ = issue ที่ติดรอบงาน (milestone) "Sprint N"
- บอร์ด GitHub Projects 5 ช่อง: รายการงาน → รอบนี้ → กำลังทำ → รอ review → เสร็จ

### กติกา

- **พร้อมหยิบ:** issue บอกเป้าหมาย บอกว่าเสร็จเมื่อไร และทำจบใน 1–2 วัน
- **ถือว่าเสร็จ:** PR ได้ approve จากคนอื่น · merge เข้า develop · อัปเดต README ของโฟลเดอร์ · ปิด issue · การ์ดอยู่ช่องเสร็จ
- **ไม่ถือหลายงาน:** คนละไม่เกิน 1 งานในช่องกำลังทำ งานที่รอ review ไม่นับ
- **review เร็ว:** PR ที่เปิดแล้ว review ภายใน 1 วัน · หมุนคน review ไม่ review งานของคนเดิมซ้ำทุกครั้ง
- **ปิดขั้น:** จบรอบ 4, 6 และ 9 เปิด PR develop → main
- **ทุกคนรู้ทุกส่วน:** รอบ 8–9 ซ้อมถามตอบ สุ่มคน สุ่มเรื่อง

Git workflow กับกติกา PR → [`../CONTRIBUTING.md`](../CONTRIBUTING.md)
