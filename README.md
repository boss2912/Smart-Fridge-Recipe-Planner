## 🎯 Smart Fridge คืออะไร

หลายครัวเรือนใช้ระบบนี้ร่วมกัน ของที่ซื้อเข้าตู้ สมาชิกแต่ละบ้านจะบันทึกเป็นล็อต พร้อมวันซื้อ วันหมดอายุ และจำนวน จากนั้นระบบก็เตือนของที่ใกล้หมดอายุ และแนะนำเมนูที่ทำได้จากของที่ยังเหลืออยู่ในตู้

### ของในตู้เข้าทางเดียว ออกได้สองทาง

```text
ซื้อ ──► ล็อตในตู้ (วันซื้อ / วันหมดอายุ / จำนวน)
            │
            ├──► ทำอาหาร ──► ระบบหักวัตถุดิบตามสูตร
            │
            └──► ทิ้ง (หมดอายุหรือเสีย) ──► หักจากล็อตนั้น และเก็บประวัติการทิ้ง
```

จำนวนในตู้จึงเท่ากับของที่ซื้อ หักของที่ใช้ทำอาหาร และหักของที่ทิ้ง ถ้าไม่บันทึกทางออกทางใดทางหนึ่ง จำนวนในตู้จะมากกว่าของจริงไปเรื่อยๆ ระบบก็จะแนะนำเมนูที่ของหมดไปแล้ว

### ผู้ใช้ 2 กลุ่ม

| ผู้ใช้ | ทำอะไรได้ |
|---|---|
| สมาชิกในครัวเรือน | บันทึกของที่ซื้อเข้าตู้ · บันทึกว่าทำเมนูไหน · บันทึกของที่ทิ้ง · ดูคำเตือนและเมนูที่ทำได้ |
| ผู้ดูแลระบบ | เพิ่มและแก้ไขรายการวัตถุดิบและสูตรอาหารกลางที่ทุกบ้านใช้ร่วมกัน |

### ข้อมูลหลัก 8 อย่าง

1. ข้อมูลครัวเรือน
2. ข้อมูลสมาชิก
3. ข้อมูลหมวดหมู่และวัตถุดิบ (หน่วยมาตรฐาน)
4. ข้อมูลของในตู้แต่ละล็อต (วันซื้อ/วันหมดอายุ/จำนวน)
5. ข้อมูลสูตรอาหาร
6. วัตถุดิบที่ใช้ในแต่ละสูตร (ปริมาณ)
7. ประวัติการทำอาหาร
8. ประวัติการทิ้งของ (ล็อต/จำนวน/วันที่ทิ้ง)

รายการซื้อของกับราคาสินค้าไม่อยู่ในขอบเขต เหตุผลอยู่ใน [`docs/DECISIONS.md`](docs/DECISIONS.md)

## 🏗️ สถาปัตยกรรม — Distributed System

ระบบแบ่งเป็น 4 ส่วน คือ Nginx (ทางเข้า) · frontend (หน้าเว็บ) · backend (API) · database (DBMS) ผู้ใช้ทั้ง 2 กลุ่มเข้าใช้ผ่านเบราว์เซอร์

```text
        Browser (สมาชิกในครัวเรือน / ผู้ดูแลระบบ)
                          │
                          ▼
                 ┌─────────────────┐
                 │      Nginx      │  ทางเข้าเดียว
                 └────────┬────────┘
              ┌───────────┴───────────┐
              ▼                       ▼  /api/
     ┌─────────────────┐     ┌─────────────────┐
     │    frontend     │     │     backend     │  API + ล็อกอิน
     └─────────────────┘     └────────┬────────┘
                                      ▼
                             ┌─────────────────┐
                             │    database     │  DBMS (ยังไม่เลือก)
                             └─────────────────┘
```

### แต่ละส่วนต้องมีอะไร

| ส่วน | ต้องมี |
|---|---|
| **Nginx** | ทางเข้าเดียวของระบบ: ส่งไฟล์หน้าเว็บของ frontend ให้เบราว์เซอร์ · ส่งต่อคำขอ `/api/` ไปที่ backend |
| **frontend** | หน้าของสมาชิกในครัวเรือน: บันทึกของที่ซื้อเข้าตู้ · บันทึกว่าทำเมนูไหน · บันทึกของที่ทิ้ง · ดูของใกล้หมดอายุ · ดูเมนูที่ทำได้<br>หน้าของผู้ดูแลระบบ: เพิ่มและแก้ไขรายการวัตถุดิบกับสูตรอาหารกลาง |
| **backend** | API ที่หน้าเว็บเรียกใช้ · ล็อกอิน · แยกสิทธิ์ 2 กลุ่ม: วัตถุดิบกับสูตรกลางแก้ได้เฉพาะผู้ดูแลระบบ และสมาชิกทิ้งได้เฉพาะของในตู้บ้านตัวเอง ([ADR-003](docs/DECISIONS.md#adr-003--ต้องมีการบันทึกการทิ้งของ)) |
| **database** | ข้อมูลหลัก 8 อย่าง · PK / FK / NOT NULL / UNIQUE ตามตัวอย่างหน้า 31 · query 4 เรื่องใน [`database/`](database/) ซึ่งทำอาหารกับทิ้งของต้องอยู่ในธุรกรรมเดียว ([ADR-001](docs/DECISIONS.md#adr-001--ทำอาหารแล้วระบบหักวัตถุดิบตามสูตร)) · DBMS ยังไม่เลือก ([ADR-005](docs/DECISIONS.md#adr-005--เลือก-dbms)) |

> งานส่ง 4 ชิ้นของอาจารย์ (Lecture 1 หน้า 11) ไม่มีหน้าเว็บหรือ API ส่วน Nginx · frontend · backend จึงเป็นงานเพิ่มนอกงานส่ง

## 🌿 Git Workflow (ร่าง)

```text
main ──────────────────────────────●  ฉบับส่งอาจารย์เท่านั้น
                                   ↑ PR
develop ───●───●───●───●───●───●───●  รวมงานทุกคน ตรวจก่อนเข้า main
           ↑       ↑       ↑
      branch งานแต่ละชิ้น (ตั้งชื่อตามเลข issue)
```

- งานทุกอย่างทำบน branch ของตัวเอง แล้วเปิด PR เข้า `develop`
- ต้องมีคนอื่นรีวิวอย่างน้อย 1 คนก่อน merge
